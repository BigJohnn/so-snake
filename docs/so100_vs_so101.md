# SO-100 vs SO-101: which URDF do we use?

**Decision: use SO-100's own URDF, patched with a TCP frame we derive from SO-101.**

SO-101's URDF ships a `gripper_frame_link` that SO-100's does not, and lerobot's
`RobotKinematics` targets that frame by name. The tempting shortcut is to just
use the SO-101 URDF. This document records why we don't, and what we did instead.

Reproduce everything below with:

```bash
git clone --depth 1 --filter=blob:none --sparse \
    https://github.com/TheRobotStudio/SO-ARM100.git /tmp/soarm
(cd /tmp/soarm && git sparse-checkout set Simulation)
export SOARM_UPSTREAM=/tmp/soarm

python scripts/compare_so100_so101.py   # the comparison
python scripts/derive_so100_tcp.py      # the TCP transfer
python scripts/check_kinematics.py      # FK/IK validation of the result
```

## Naive comparison is misleading

Comparing joint-origin offsets (`|origin|`) between the two URDFs suggests the
shoulder and wrist were mechanically redesigned:

| joint segment | SO-100 | SO-101 | delta |
|---|---|---|---|
| shoulder_pan | 48.12 mm | 73.50 mm | +25.4 mm |
| shoulder_lift | 106.97 mm | 64.78 mm | −42.2 mm |
| elbow_flex | 116.00 mm | 116.00 mm | 0.00 mm |
| wrist_flex | 135.00 mm | 135.00 mm | 0.00 mm |
| wrist_roll | 60.10 mm | 63.72 mm | +3.6 mm |
| gripper | 31.68 mm | 36.18 mm | +4.5 mm |

**This metric is not valid.** A revolute joint's frame origin only has to lie
*on* its rotation axis — it can slide freely along that axis without changing
the mechanism. The two URDFs place their frames differently, so these numbers
mix real geometry with frame bookkeeping.

## Invariant comparison: the arms are kinematically identical

The common-normal distance and twist angle between consecutive rotation axes
(the DH parameters `a` and `alpha`) are invariant under *any* choice of link
frames. Measured at zero configuration:

| axis pair | SO-100 | SO-101 | delta |
|---|---|---|---|
| shoulder_pan → shoulder_lift | 30.60 mm / 90° | 30.40 mm / 90° | −0.20 mm |
| shoulder_lift → elbow_flex | 116.00 mm / 0° | 116.00 mm / 0° | 0.00 mm |
| elbow_flex → wrist_flex | 135.00 mm / 0° | 135.00 mm / 0° | 0.00 mm |
| wrist_flex → wrist_roll | 0.00 mm / 90° | 0.00 mm / 90° | 0.00 mm |
| wrist_roll → gripper | 20.20 mm / 90° | 20.20 mm / 90° | 0.00 mm |

Every segment agrees, the worst deviation being 0.20 mm at the shoulder —
modelling round-off, not a design change. **SO-100 and SO-101 are the same
kinematic chain.**

## What actually differs, and why we still don't swap URDFs

| difference | consequence |
|---|---|
| **Zero-configuration convention** — the shoulder_pan→wrist_roll twist is 70.43° on SO-100 vs 90.00° on SO-101 | the same joint vector means a *different physical pose* in each URDF; using the wrong one needs a per-joint offset remap, and getting that wrong is a centimetre-scale error |
| **Joint limits** — e.g. `shoulder_lift` is `[0, 3.5]` on SO-100 vs `[-1.745, 1.745]` on SO-101 | gates which IK solutions exist and where the M3 safety layer clamps |
| **Meshes** — all 13 STL filenames differ, no overlap | irrelevant to IK, but M3 collision checking needs the right geometry |
| link naming, axis conventions | pure code adaptation, harmless |

The kinematic equivalence is good news — it means SO-101-derived tuning largely
transfers — but it is not a reason to swap URDFs. Doing so would buy us a
10-line dummy link at the cost of owning a joint-offset remap, which is exactly
the error-prone part.

## Transferring the TCP

Because the axis geometry *is* identical, SO-101's official TCP transfers to
SO-100 exactly rather than being estimated. `scripts/derive_so100_tcp.py`:

1. builds a frame `G` attached to the gripper link from physical features only —
   origin at the point on the gripper (jaw) axis closest to the wrist_roll axis,
   `z` along the gripper axis, `x` along the common normal;
2. expresses SO-101's `gripper_frame_link` in `G`;
3. maps those coordinates onto SO-100's `G` and back into SO-100's `gripper` link.

Result, now baked into `assets/urdf/so100/so100.urdf`:

```xml
<joint name="gripper_frame_joint" type="fixed">
  <origin xyz="0.007900 -0.099127 -0.000218" rpy="1.570800 0 0"/>
  <parent link="gripper"/>
  <child link="gripper_frame_link"/>
</joint>
```

Two independent cross-checks:

- the TCP sits **79.8363 mm** from the gripper axis on both robots (preserved by
  construction, so this validates the implementation);
- the derived offset is SO-101's own value under an axis permutation —
  SO-101 `(-0.0079, -0.000218, -0.0981)` vs SO-100 `(0.0079, -0.0991, -0.000218)`
  — exactly what the differing frame conventions predict.

## Validation

`scripts/check_kinematics.py` round-trips FK → IK → FK over 50 random in-limit
configurations:

```
position error    median  0.0141 mm   p95  0.0777 mm   max  0.0936 mm
rotation error    median  0.0001 deg  p95  0.0042 deg  max  0.0081 deg
```

## Open item: base frame convention

At zero configuration the TCP lands at `(-0.0002, -0.2374, +0.0956)` m. SO-100's
base frame has **Z up but the arm extending along −Y**. For teleoperation we
want "push the stick forward" to mean +X, so a `T_world_base` rotation is
needed. This is handled in configuration rather than by editing the URDF, to
keep our asset diffable against upstream.

**Everything above is geometry from the URDFs — none of it is verified against
the physical arm.** Real-hardware calibration (servo zero offsets, actual TCP
under a closed gripper) is a Phase 0 on-hardware task.
